Google Trends for a Historical Window

A decision document for the news project. The project reconstructs a past window: you give a start date and an end date and see only what existed inside them. This page inventories every function the pytrends library exposes, says which ones still work, marks which ones can be pointed at a past window, and recommends building exactly one of them. Every status below was re-tested against the live endpoints from this machine on 2026-08-10. Nothing is implemented in the project yet.

The function that matters. interest_over_time with an explicit start and end date -- the search-attention series for chosen keywords across a window that has already passed. Everything else is either broken, aimed at the present moment, or a second data shape the project does not need. Section 2 shows the evidence for each.

1. What the Number Means

Google Trends reports how often people typed a term into Google search, expressed as a relative index from 0 to 100. The value 100 is assigned to the moment of highest search volume within the window you requested; every other value is scaled against that peak.

Concretely: if "bitcoin" scores 100 on 2015-05-12 and 50 on 2015-06-03, people searched it half as much on June 3 as at the May peak. Request a wider window containing a bigger spike and both numbers shrink, because the scale re-anchors to the new peak. Section 5 shows a measured example of that and explains why it is dangerous for a backtest. Two consequences up front:

  • No absolute counts, ever. You learn the shape of attention over time, not how many searches happened.
  • Numbers are comparable only within one response. Requesting several keywords together (up to five) puts them on one shared scale, which is the only honest way to compare keywords.

For this project it is a public-attention series covering the same days as the articles. Articles say what was published; Trends says what ordinary people were curious about during those same days, including things the press had not covered yet. The gap between the two is the reason to want it, and it only means something when both sides cover identical dates.

5. The Scaling Trap, and What to Do About It

Write $v_t$ for the true, unobservable search volume on day $t$. For the requested window $[s, e]$, what Google returns is

$$ I_t^{[s,e]} \;=\; \mathrm{round}\!\left( 100 \cdot \frac{v_t}{\max_{s \le u \le e} v_u} \right) $$

Every symbol: $I_t^{[s,e]}$ is the reported index on day $t$ from a request covering $s$ to $e$; $v_t$ is the true volume on day $t$; the denominator is the largest true volume on any day in the window, including days after $t$. That last part is the whole problem. A series fetched for all of 2017 tells every January value where the May peak was. If a study stands on 2017-01-05 and reads a number, that number already knows the future. This is look-ahead bias arriving through the normalization rather than through data selection, so the project's publication-date filter cannot catch it.

When it hurts and when it does not

The leak is one constant divisor applied to the whole series, exactly as the ratio column in section 4 shows. That gives a clean rule:

  • Scale-invariant use is nearly safe. Ratios, percentage changes, log differences, and z-scores computed only from data up to the decision date are unchanged when the entire series is multiplied by a constant. The future peak cancels.
  • Level-dependent use leaks. Any rule like "index above 80", or comparing raw levels between two series fetched over different windows, reads the future peak directly. In section 4 the same day is both above and below any threshold you might pick.
  • Rounding leaks a little even in the safe case. Values are integers from 0 to 100. A large later spike compresses earlier values toward zero, so a quiet stretch that should read 3.4 and 2.6 both arrive as 3. That precision loss is a function of future data and no scale-invariant arithmetic recovers it.

The fix

If a study makes a decision on date $d$, request $[s, d]$ instead of $[s, e]$ with $e > d$. The denominator becomes $\max_{s \le u \le d} v_u$, knowable at $d$. Stepping through many decision dates therefore means an expanding-window fetch: one request per decision date, each ending on that date. Honest, but a daily study over one year is roughly 250 requests for one keyword set against a rate-limited unofficial endpoint. Two cheaper options:

  1. Rebase locally. Fetch one long window, then for each decision date $d$ divide the series by its own running maximum up to $d$. One request instead of hundreds, and it reproduces the as-of scale exactly unless rounding already flattened the early values.
  2. Use only scale-invariant features, and keep the window as short as the study allows so the peak stays near the data you care about.
Rule to encode in the wrapper: never return or store a series without the window it was fetched with. A bare 0-100 series with no window attached cannot be audited for this bias, and looks perfectly reasonable while being wrong.

6. Getting Daily Values Across More Than 9 Months

Ask for a window longer than about 9 months and Google downgrades you to weekly (section 3). Three ways out, in order of preference.

ApproachHow it worksCost and caveats
Manual stitching (recommended) Fetch overlapping windows of at most 9 months. For adjacent windows $A$ and $B$ sharing overlap $O$, compute $k = \left(\sum_{t \in O} x^A_t\right) / \left(\sum_{t \in O} x^B_t\right)$, replace every value of $B$ with $k \cdot x^B_t$, and concatenate. Repeating forward puts the whole history on the first window's scale. Roughly two requests per year of history, plus repeats for noise averaging. Seam errors compound along the chain, so fetch each window more than once and average before stitching. Supports up to 5 keywords, since it is just repeated normal requests.
pytrends.dailydata.get_daily_data The library's own helper. Fetches one month at a time for daily shape, plus one long request for the monthly level, then multiplies the daily values by the monthly level to put everything on a common scale. Verified working: January to February 2017 returned 59 rows with unscaled, monthly, scale, and the combined column. Three real limits. One keyword per call, so no shared-scale comparison. One request per month means a ten-year history is about 120 requests with a built-in wait between each. And the method only makes sense when the overall range exceeds 9 months; below that the "monthly" request itself returns daily data and the rescaling degenerates. Output values are not integers and no longer max at 100, which is fine but breaks any code expecting the 0-100 convention.
get_historical_interest The old built-in for long hourly history. Removed. Calling it raises NotImplementedError with a note that it was withdrawn for incorrectness and will be deleted in version 5. Any tutorial recommending it is out of date.

7. Other Limits That Matter

  1. Revisions: today's fetch of 2015 is not what 2015 looked like. Google recomputes from its current sample with its current methodology. Correct as-of windowing removes the normalization leak, not this one. The only complete fix is storing every fetch with its timestamp and building a dated archive going forward, which does nothing for windows before you start.
  2. Sampling noise. The index comes from a sample of searches, so the identical request twice can return slightly different values. Careful use fetches several times and averages.
  3. Rate limiting. The endpoints are unofficial and aggressively rate limited (HTTP 429 after bursts). The probe run behind this page needed several seconds of spacing between calls to complete. Any repeated, stitched, or expanding-window use needs a cache and delays; treat that as part of the feature, not a later optimization.
  4. Low-volume censoring. Terms below a threshold return 0, which reads as "no interest" when it means "not enough data". Visible twice in the samples above: ethereum across all of 2015, and the news search property returning mostly zeros. Older windows are more exposed, because a term common now may have been rare then.
  5. Keyword meaning drifts. The same string searched in 2012 and in 2024 can refer to different things. Using the entity identifier from suggestions() instead of the raw string reduces this without removing it.

10. Implementation Blueprint

A full implementation was built, verified against the live endpoints, and then removed so features could be chosen deliberately. It lives in git history: commit 38ff678 added it, commit 3a70fac reverted it. It covered three functions; only one is now wanted, so restoring it is a subset, not a revert.

Design decisions worth keeping, and why

  • Trends is its own package, not a news provider. The article process converts records into one common format, filters, and deduplicates. A 0-100 time series fits none of that, so forcing it into the provider registry would corrupt both abstractions.
  • The library hides behind one interface. Route, CLI, and tests depend on a small TrendsClient interface; only one module imports pytrends. When the archived library breaks, the swap touches one file.
  • Synchronous route handler on purpose. The library blocks on HTTP; declaring the FastAPI route as a plain function makes the framework run it in its worker thread pool, keeping the async event loop free for article searches.
  • The CLI skips the server. Trends needs no server-held credentials and no coordination across sources, so news-trends calls the package directly and works without a running server.
  • Errors map by fault. Bad inputs (empty keywords, more than five, bad dates) return HTTP 422; Google failures, including rate limits, return HTTP 502 with a plain-language message.
  • Tests stay offline. Fake clients and fake DataFrames cover conversion, validation, retry rules, route output, and CLI display -- the same policy the project applies to news providers, since live Google behavior is not deterministic.

Three changes that build needs before it returns

  1. Take a start date and an end date, not a timeframe string. Build the timeframe internally and never expose the today-anchored shorthands. This alone removes present-moment behavior from the interface, so it cannot be called by accident.
  2. Store the window and the granularity, not just fetched_at. The timestamp says when the request ran; the window says what the 0-100 scale is anchored to, which section 5 makes the load-bearing field. The granularity says whether the caller got hourly, daily, or weekly values, which the dates decide silently.
  3. Default the window to the news search window. When called from the browser, the trends dates should be the article dates. Any divergence should be an explicit choice, never a default.

How to restore

  • Bring the files back, then delete what is out of scope: git checkout 38ff678 -- src/news/trends/, then remove the region and related-query models, routes, and CLI subcommands.
  • git revert 3a70fac restores all three functions, so it is the wrong starting point unless the scope decision changes.

TL;DR

Tested live on 2026-08-10: every pytrends function that reports "what is popular right now" is dead (trending searches, today's searches, real-time trending, top charts, all HTTP 404), and so are related topics and multirange comparison. Everything that takes a date window still works -- interest over time, related queries, interest by region -- plus suggestions for entity identifiers and categories for filtering. The project needs one of them: interest over time with explicit start and end dates, which also delivers hourly resolution for any past week and can be stitched past the 9-month daily limit. The trap to design around is the 0-100 scale, divided by the peak of the whole requested window: a measured example shows 2017-01-05 reading 100 in one window and 30 in another, with a constant ratio, because the long window's peak sits in May. Scale-invariant features survive that; level thresholds do not. Fix it by ending the window on the decision date or rebasing to a running maximum, and always store the window next to the values. Free access rides on an archived library, so keep it behind a one-method interface. Section 9 is the build list; section 10 shows how to restore the matching subset from git history and the three changes it needs first.
