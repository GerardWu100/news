Google Trends: What the Data Can Provide

A decision document for the news project. It explains what Google Trends measures, every data type that is currently retrievable for free, the request options, the limits that matter for quantitative research, and a menu of features that could be built. Nothing described here is implemented; this page exists so you can choose.

1. What Google Trends Measures

Google Trends reports how often people typed a term into Google search, expressed as a relative index from 0 to 100. The value 100 is assigned to the moment of highest search volume within the window and keyword set you requested; every other value is scaled against that peak.

Concretely: if "bitcoin" scores 100 on May 12 and 50 on June 3, people searched it half as much on June 3 as at the May peak. But if you re-request a wider window that contains an even bigger spike, both numbers shrink, because the scale is anchored to the new peak. Two consequences follow:

  • No absolute counts, ever. You cannot learn how many searches happened, only the shape of attention over time.
  • Numbers are only comparable within one response. Requesting several keywords together (up to five) puts them on one shared scale, which is how cross-keyword comparison is done.

This is a public attention signal. It complements the news project's article retrieval: articles say what was published; Trends says what ordinary people were actively curious about, including things the press had not covered yet.

3. Request Options

OptionValuesNotes
Keywords 1 to 5 per request All keywords in one request share one 0-100 scale. Comparing more than 5 requires overlapping batches and rescaling through a shared anchor keyword.
Timeframe today 3-m, today 12-m, today 5-y, all, now 7-d, or explicit dates 2025-01-01 2025-06-30 Historical data reaches back to 2004. The window length dictates granularity (next table).
Geography "" worldwide, US country, US-NY state, CA Canada, ... Standard two-letter country codes with optional region suffix.
Category About 1,400 numeric Google categories For example Finance or Investing; restricts which searches count, disambiguating terms like "apple".
Search property Web (default), News, Images, YouTube, Shopping News-search-only interest is possible and thematically close to this project.

Granularity is decided by window length

Requested windowGranularity you receive
Up to about 7 daysHourly
About 7 days to 9 monthsDaily
9 months to 5 yearsWeekly
More than 5 yearsMonthly

You cannot ask for daily values over 3 years directly. Getting a long daily history requires fetching overlapping shorter windows and stitching them by rescaling through the overlap -- a known technique, but it must be built deliberately.

4. Limits That Matter for Quantitative Research

  1. Relative scaling. Every number depends on the window and keyword batch it was fetched with. Series fetched at different times or with different windows are not directly comparable without rescaling.
  2. Sampling noise. Google computes the index from a sample of searches. Fetching the identical request twice can return slightly different values. Serious research fetches several times and averages.
  3. Not historical as-of data. Today’s fetch of 2025 data is not what you would have seen in 2025. Backtesting on freshly fetched history carries revision risk. The honest fix is storing every fetch with its timestamp and building your own dated archive going forward.
  4. Rate limiting. The endpoints are unofficial and aggressively rate limited (HTTP 429 after bursts). Bulk collection needs spacing, retries, and ideally caching.
  5. Low-volume censoring. Terms or regions below a volume threshold return 0 or are omitted entirely, which can look like "no interest" when it means "not enough data".

Whatever the route, the sane design is one thin internal interface with the chosen library isolated behind it, so a dead library is a one-file swap and the rest of the project never notices.

7. Implementation Blueprint

A complete implementation was built, verified against the live endpoints, and then removed so features could be chosen deliberately. It lives in git history: commit 38ff678 added it, commit 3a70fac reverted it, so any subset can be restored without rewriting. This section records that design and the ideas that go beyond it.

Design decisions worth keeping, and why

  • Trends is its own package, not a news provider. The article process converts records into one common format, filters, and deduplicates. A 0-100 time series fits none of that, so forcing it into the provider registry would corrupt both abstractions.
  • The library hides behind one interface. Routes, CLI, and tests depend on a small TrendsClient interface; only one module imports pytrends. When the archived library breaks, the swap (to trendspyg or the official API) touches one file.
  • Synchronous route handlers on purpose. The library blocks on HTTP; declaring the FastAPI routes as plain functions makes the framework run them in its worker thread pool, keeping the async event loop free for article searches.
  • The CLI skips the server. Unlike article search, Trends needs no server-held credentials and no coordination across sources, so news-trends calls the package directly and works without a running server.
  • Errors map by fault. Bad inputs (empty keywords, more than five, bad resolution) return HTTP 422; Google service failures, including rate limits, return HTTP 502 with a plain-language message.
  • Every result carries fetched_at. Because Google samples and rescales, a stored result is only meaningful together with when it was fetched. Recording it from day one makes a future point-in-time archive possible.
  • Tests stay offline. Twenty-three tests covered frame conversion, validation, retry rules, route output, and CLI display through fake clients and fake DataFrames -- the same policy the project applies to news providers, since live Google behavior is not deterministic.

Ideas beyond the previous build

Menu itemImplementation sketch
4. Browser integration Add a trends panel to the existing frontend that calls /api/trends/interest with the search window's dates as an explicit timeframe, so the chart shows attention during the same historical period as the articles. Needs a small chart renderer and a date-window bridge from the search form.
5. Long daily history Fetch overlapping windows of at most 9 months, then rescale each window so values agree on the overlap (divide by the ratio of overlapping means) and concatenate. The seams inherit sampling noise, so fetch each window more than once and average before stitching.
6. Point-in-time archive A table keyed by (keyword set, timeframe, geo, fetched_at) storing the raw series -- SQLite through the existing export layer, or ClickHouse for research joins. A scheduled daily fetch of a fixed keyword list turns the relative-index problem into your own absolute history going forward.
7. Caching and rate limits Reuse the search cache pattern: a short time-to-live in-process cache keyed by the full request, plus the existing cooldown idea from the news providers (after a 429, fail fast locally for a window instead of hammering Google).
More than 5 keywords Batch keywords with one shared anchor keyword in every batch, then rescale all batches onto the anchor's scale. Doubles or triples request count, so it depends on caching being in place first.
8. Wikipedia pageviews A sibling package with the same interface shape, calling the official Wikimedia pageviews API: absolute daily counts, no sampling, no relative scaling, generous limits. Cross-checking both attention measures guards against artifacts in either.

How to bring any of it back

  • A subset: restore files from 38ff678 (for example git checkout 38ff678 -- src/news/trends/) and trim routes, CLI, and docs to the chosen features.

TL;DR

Google Trends can give the project four working data types -- attention over time, attention by region, companion queries (top and rising), and entity disambiguation -- filtered by window, geography, category, and search property, back to 2004. All values are a relative 0-100 index shaped by sampling, window-dependent granularity, and rate limits; none are absolute counts, and none are point-in-time safe without building an archive. Free access rides on unofficial libraries (working today, breakable tomorrow), so any implementation should hide the library behind one replaceable interface. Pick features from the menu in section 6; section 7 records the verified implementation design sitting in git history, ready to restore in part or in full.
